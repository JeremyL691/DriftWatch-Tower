# Management Console Implementation Plan

**Goal:** Complete both management batches: existing operational actions and persisted online configuration of detector rules/thresholds and the existing single GitHub collector; validate before committing/pushing a feature branch.

**Architecture:** Keep the Spring Boot/Kafka Streams/PostgreSQL monolith and static dashboard. Reuse existing authenticated operational APIs. Persist validated configuration revisions in PostgreSQL, separating saved configuration from the effective runtime snapshot and explicitly marking restart-dependent fields. Preserve environmental credential management and stream-state invariants.

**Tech Stack:** Java21, Spring Boot3.5, Kafka Streams, PostgreSQL/Flyway, static JavaScript/CSS, JUnit/Testcontainers, Node and Playwright acceptance tooling.

## Scope and invariants
- First batch: alert status filters/acknowledge/resolve; schema version comparison, activation and truthful publication status; collector timing/checkpoint/outbox/gaps/health; event detail/evaluation/linked alerts; retention status/confirmed run; dead-letter replay result/history.
- Second batch: real validated persisted detector rules and thresholds plus existing single GitHub collector settings. Show effective/saved values, operation history, and restart requirements. Invalid writes do not mutate configuration; concurrent stale edits must not overwrite newer revisions.
- No notification feature, 24h soak, multi-collector scheduling, tenant/account features, new connector or front-end framework.
- Preserve startup defaults and env credentials, existing endpoints, source identities/checkpoints, idempotency and fault recovery. No secrets in management API/audit history/browser storage or logs.
- Threshold changes must actually reach detector consumers. Do not promise runtime application of stateful window changes or in-flight collector changes without proof. Kafka topic publication is not proof every Streams consumer applied a schema baseline.
- Approved supervisor safeguard on recovery: namespace only null/anomaly window counts/fired flags, their window watermarks and anomaly observation state by a deterministic versioned fingerprint of effective startup window/grace/future/retention/baseline/history policy. Pending or live-only changes must not change this identity. Preserve all ingestion/delivery/duplicate identities, external evaluation scopes, schema baselines, checkpoints, outboxes, topics and store names. Old/legacy policy state needs demonstrably bounded safe cleanup, not permanently frozen watermarks; rejected future events must not drive eviction. Document safe legacy warm-up and test persisted same/different-policy restart, equal-boundary collisions, live-only preservation and retained/expired switch-back behavior. Broader migrations require another supervisor decision.
