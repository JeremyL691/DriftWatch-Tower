# DriftWatch Tower runbook

Operational procedures for a self-hosted install. Every command takes an explicit `--project` and
`--env-file`; nothing here touches containers or volumes it does not own.

For the HTTP examples below, load the credentials generated by `init` without printing them:

```bash
set -a
source .execution/selfhost.env
set +a
DWT_BASE="http://127.0.0.1:${DWT_APP_PORT:-18080}"
```

## Install

```bash
git clone https://github.com/JeremyL691/DriftWatch-Tower.git
cd DriftWatch-Tower
scripts/selfhost.sh init --env-file .execution/selfhost.env   # random credentials, mode 0600
scripts/selfhost.sh up   --env-file .execution/selfhost.env
```

`init` generates the PostgreSQL password, the admin password and the ingest token. The file is
created with mode 0600 and is ignored by git. To use the published image instead of building,
set `DWT_APP_IMAGE=ghcr.io/jeremyl691/driftwatch-tower@sha256:<digest>` in the env file; compose
pulls that digest and never rebuilds it.

Check readiness (readiness reflects PostgreSQL, Kafka and the Kafka Streams runtime, so a
container that is up but not processing does not report healthy):

```bash
curl -fsS http://127.0.0.1:18080/actuator/health/readiness
```

## Upgrade

For a historical upgrade that changes the Kafka envelope contract, follow the paired database
and stopped-Kafka-volume backup procedure below before starting the new application. Preserve
the original topics, partition cutoffs and consumer offsets. The basic image update is:

1. Back up first: `scripts/selfhost.sh backup --env-file .execution/selfhost.env --out backup/pre-upgrade.dump`
2. Point `DWT_APP_IMAGE` at the new digest.
3. `docker compose -p driftwatch --env-file .execution/selfhost.env up -d app`

Flyway applies any new migration on start. Migrations V1–V7 are frozen: they are never edited, so
the schema history of an existing install stays consistent. An older image may still start
against a newer schema; startup is not evidence of a supported rollback. Stop new ingestion,
save the current evidence and restore the pre-upgrade PostgreSQL and Kafka-volume backups
with the historical image. Image-only rollback across this contract change is unsupported.

## Backup and restore

```bash
scripts/selfhost.sh backup  --env-file .execution/selfhost.env --out backup/dwt.dump
scripts/selfhost.sh restore --env-file .execution/selfhost.env --dump backup/dwt.dump --target-db driftwatch_restore
```

`restore` always targets a new database; it never overwrites a live one. A verified restore is
part of the release evidence: the row counts of raw events, alerts, schema versions and receipts
must match the source at the backup boundary, including collector checkpoints and inbox/outbox
contents. Check receipt/raw correspondence at that boundary. Normal retention can later leave
recent deduplication receipts after expired raw rows have been removed.

Kafka offsets and a PostgreSQL backup are separate recovery boundaries. A database-only restore
does not rewind committed Kafka offsets, so restarting alone cannot guarantee recovery of rows
processed after that backup. For the historical upgrade drill, stop ingestion, drain and record
each partition's offsets, stop the application and back up the database plus the stopped Kafka
volume. Restore both to fresh acceptance resources and reconcile the ledger before resuming.
Keep the original topics and recovery evidence. Processed receipts make replay of the same
retained ingestion identities idempotent within the documented retention limits.

## Day-to-day checks

```bash
scripts/selfhost.sh status --env-file .execution/selfhost.env
curl -u "$DWT_ADMIN_USERNAME:$DWT_ADMIN_PASSWORD" http://127.0.0.1:18080/api/v1/sources/collectors
curl -u "$DWT_ADMIN_USERNAME:$DWT_ADMIN_PASSWORD" http://127.0.0.1:18080/api/v1/operations/retention
```

`collectors` reports per-source `last_poll_at`, `last_success_at`, `next_poll_at`, upstream lag,
pending outbox rows, open gaps and any backoff. A source that stops appearing is reported as
`LOST` rather than silently stale; a successful poll with no new events is `QUIET`.

### Synthetic detector demos

An admin-only endpoint exercises the detectors with generated events, which is useful for
confirming that alerting works before real traffic arrives:

```bash
admin_post /api/v1/demo/run-scenario/duplicate-events
```

Scenarios: `normal-flow`, `duplicate-events`, `late-events`, `null-spike`, `anomaly-spike`,
`stale-source`, `mixed-incident`, `schema-drift`, `field-range`, `field-format`. Their events carry `source` values starting with `demo` (for
example `demo-api`), so they stay distinguishable from real source data everywhere. Nothing
collected from the GitHub source is ever synthesised, and the acceptance evidence counts only
rows whose origin is `GITHUB`. Treat those rows as test data: ignore them when reading the
dashboard, and filter them out before archiving an environment.

Define the `admin_post` helper in the protected administrative requests section before using
this command. Synthetic demo rows have origin `REST` and mode `SYNTHETIC`.

## Dead letters

```bash
curl -fsS -u "$DWT_ADMIN_USERNAME:$DWT_ADMIN_PASSWORD" "$DWT_BASE/api/v1/dead-letters?status=OPEN"
```

A dead letter carries its original topic, partition, offset and a stable diagnostic id. Replay
re-enters the pipeline at the stage that failed and returns a new attempt id; it is safe to run
twice, because the sink's processed receipts make the second attempt a no-op. A replay the
broker did not acknowledge answers 503 with outcome `FAILED`; the record stays open, so retry it.

## Protected administrative requests

Demo actions, replay, retention and alert changes require both Basic authentication and a CSRF
cookie/header pair. This helper obtains the real cookie from an authenticated read before each
POST. Keep its temporary cookie jar private and remove it after the command:

```bash
admin_post() {
  local dwt_cookie_file dwt_csrf dwt_status
  dwt_cookie_file=$(mktemp)
  chmod 600 "$dwt_cookie_file"
  if ! curl -fsS -u "$DWT_ADMIN_USERNAME:$DWT_ADMIN_PASSWORD" -c "$dwt_cookie_file" \
    "$DWT_BASE/api/v1/operations/retention" >/dev/null; then
    rm -f "$dwt_cookie_file"
    return 1
  fi
  dwt_csrf=$(awk '$6 == "XSRF-TOKEN" {print $7}' "$dwt_cookie_file" | tail -1)
  if [ -z "$dwt_csrf" ]; then
    rm -f "$dwt_cookie_file"
    return 1
  fi
  curl -fsS -u "$DWT_ADMIN_USERNAME:$DWT_ADMIN_PASSWORD" -b "$dwt_cookie_file" \
    -H "X-XSRF-TOKEN: $dwt_csrf" -X POST "$DWT_BASE$1"
  dwt_status=$?
  rm -f "$dwt_cookie_file"
  return "$dwt_status"
}

admin_post /api/v1/demo/run-scenario/duplicate-events
# Choose an actual ID from the dead-letter list before running replay:
# admin_post "/api/v1/dead-letters/$DWT_DLT_ID/replay"
admin_post /api/v1/operations/retention/run
```

## Persisted management configuration

See [Management configuration API](management-configuration-api.md) for complete requests, bounds,
revision/conflict semantics and supporting console endpoints. Admin-only GET/PUT
`/api/v1/configuration` separates saved and effective snapshots; PUT requires the same CSRF
cookie/header pair as other browser mutations. Flyway V13 adds the singleton saved revision and
append-only successful operation history; earlier migrations are unchanged. Invalid/stale writes
never change configuration or history. Live changes publish only after their own transaction commits.

Late/null/anomaly trigger thresholds and precompiled numeric/format rules apply to subsequent
processing. Range/format field names are literal top-level payload keys, not nested path traversal.
Anomaly evaluation always requires the complete baseline-window span (WARMING_UP otherwise).
New PUT couples min_history to baseline; historical lesser startup/saved values remain readable
and are not rewritten, but do not relax full-span detection. Duplicate/window/grace/retention/baseline span and **all** GitHub settings wait for a
real restart. Pending enabled=false is not an emergency stop. After the first save, saved
nonsecret fields override startup environment defaults on restart; credentials, destinations and
infrastructure remain environment-owned. No second collector is created. Drain the old source's
pending poll/outbox work before changing repositories; old identities/checkpoints remain durable.

Window policies use a cached versioned fingerprint namespace, isolating counts/fired flags,
accepted watermarks and anomaly observation history when restart settings change. Same-policy
restart/live threshold updates preserve unexpired state. Each policy/scope has an inactivity lease
using processor wall-clock time and its owning retention. Active windows expire against the
accepted watermark, not rejected future event timestamps. Once per minute, wall-clock cleanup
removes inactive namespaces' windows and watermark/observation/lease metadata after retention;
accepted access also resets an expired lease. Downtime counts toward expiry. Switching back may
resume only still-valid state; otherwise it warms up. Upgrade deliberately warms up legacy
unnamespaced null/anomaly state instead of guessing its policy. No delivery receipt, duplicate
identity store, schema baseline, DB checkpoint/outbox, Kafka topic or store name is reset.

GET `/api/v1/configuration/history` is bounded and records authenticated actor, revision, changed
field names, result and time only. GET `/api/v1/schemas/{eventType}/baseline` shows durable
publication evidence and explicitly UNCONFIRMED consumer application. Collector reads expose
checkpoint/pending-run evidence, source-scoped backlog/gap counts and newest20 gap records;
unknown missing counts remain unknown. Never interpret publication/replay acceptance as proof
of every downstream consumer completing.

## Retention

Retention runs daily in batches of at most 1000 rows: raw events and metric windows after 30
days, resolved alerts and incidents and recovered dead letters after 90 days, source inbox
identities after 35 days. Collector poll runs older than 35 days are pruned once nothing references
them (pending checkpoint, inbox row or gap) and they fall outside the newest 20 per source; collector
gaps older than 90 days are pruned except the newest 20 per source. Unresolved alerts and incidents,
unrecovered dead letters, pending outbox rows and collector state are never pruned. Run it manually with
`POST /api/v1/operations/retention/run` when you want the counts immediately.

## Troubleshooting

| Symptom | First check |
|---|---|
| readiness stays `DOWN` | `docker compose logs app`; readiness needs PostgreSQL, Kafka and Streams, so check which component is named |
| no new GitHub events | `GET /api/v1/sources/collectors`: `QUIET` with a recent successful poll is normal; `BACKOFF`/`ERROR` names the reason, and a gap row records what could not be seen |
| ingestion answers `503` | the broker did not acknowledge within the timeout; retry with the same `Idempotency-Key` — the identity is reserved, so a retry cannot duplicate the event |
| ingestion answers `409` | the same `Idempotency-Key` was used with different content; use a new key for a new event |
| disk filling up | `GET /api/v1/operations/retention` shows protected counts; raise retention frequency or lower the windows deliberately |
| dashboard shows `Disconnected` | the socket reconnects with backoff and re-queries; check that `/ws` is reachable through your reverse proxy (it must allow WebSocket upgrades) |

## Uninstall

```bash
scripts/selfhost.sh down --env-file .execution/selfhost.env            # keeps volumes
scripts/selfhost.sh down --env-file .execution/selfhost.env --volumes  # removes them
```

Volumes are project-scoped (`<project>_pgdata`, …), so removing one install cannot affect another.
